# OpenUSD Web Engine Template

A template for bootstrapping a **Babylon.js** or **Three.js** web project
backed by a code-first **OpenUSD** asset pipeline: 3D assets are authored in
Python with the `pxr` API, not a visual editor, and exported to a
self-contained model the chosen web runtime loads.

## How it works

```
pipeline/*.py  →  public/assets/models/<name>.usdz + <name>.glb  →  src/ (Babylon.js or Three.js)
```

- **`pipeline/`** — Python scripts using the OpenUSD API to author `.usda`
  stages, then export two artifacts per asset: a self-contained `.usdz`
  (the authoritative OpenUSD interchange file, for DCC tools/review) and a
  `.glb` (what the web runtime actually loads). Both engines' USD/usdz
  import support is either missing or experimental, so `.glb` — produced by
  converting the flattened stage through headless Blender — is the asset
  the runtime depends on. See `CLAUDE.md` and the `usd-build`/
  `usd-dcc-export` Claude skills for the full rationale and authoring
  conventions.
- **`src/`** — a minimal TypeScript + Vite app loading `public/assets/models/model.glb`,
  generated by `setup.mjs` for whichever engine you pick (not present until
  you run it).

## Prerequisites

- **Node.js** (for the web runtime and `setup.mjs`)
- **conda or mamba** ([miniforge](https://github.com/conda-forge/miniforge)),
  for a full OpenUSD build: the PyPI `usd-core` wheel is a stripped build
  with no `usdchecker` CLI and no Hydra/`usdview`, so the pipeline uses
  conda-forge's `openusd` package instead.
- **Blender** (5.x+), used headlessly to convert the pipeline's USD output
  to `.glb`. Make sure `blender` is on `PATH`, or set the
  `BLENDER_EXECUTABLE` env var to its full path.

## Quick start

1. Set up the OpenUSD environment once:

   ```bash
   conda env create -f environment.yml -p ./.conda-env
   ```

   Activate `.conda-env` before running any pipeline command below.

2. Bootstrap the web project — this prompts you to choose Babylon.js or
   Three.js, then generates `package.json`, `index.html`, `src/main.ts`,
   and installs npm dependencies:

   ```bash
   node setup.mjs
   ```

3. Generate the sample asset:

   ```bash
   npm run build:assets
   ```

4. Launch the dev server:

   ```bash
   npm run dev
   ```

## Choosing a framework

| | Babylon.js | Three.js |
|---|---|---|
| Framed for | Games, interactive simulations | Cinematic video, frame-accurate captures |
| Physics | Havok (`@babylonjs/havok`) | — |
| Model loading | `AppendSceneAsync` + `@babylonjs/loaders/glTF` | `GLTFLoader` (`three/addons/loaders/GLTFLoader.js`) |

Whichever you pick, `setup.mjs` prunes the other engine's Claude skill
(`.claude/skills/babylon-engine` or `.claude/skills/three-engine`) so your
project only carries the guidance relevant to it.

## Working with Claude Code

This template ships several `.claude/skills/` that load automatically for
the relevant task: `usd-build` and `usd-dcc-export` (OpenUSD authoring and
DCC/web-loader export gotchas, framework-agnostic) plus `babylon-engine` or
`three-engine` (whichever `setup.mjs` kept). `CLAUDE.md` documents the
project's conventions and known pitfalls in more detail than this file.
